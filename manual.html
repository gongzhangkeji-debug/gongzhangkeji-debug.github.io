项目复盘 · 这一路遇到的难题与思考

时间跨度：2026-11-16 深夜 → 2026-11-17 凌晨

项目：个人作品集网站（桌面端 + 移动端 + 云服务）

这份文档记录的是真实踩过的坑，以及每个坑背后的判断逻辑。

一、九个真实难题

难题 1：视频进度条拖不动（最大的一次误判）

现象：视频能播放，但拖动进度条后松手会跳回开头。桌面、手机、不同域名都一样。

我最初的错误判断：以为是前端代码问题，于是反复改：

  • 换封面实现（自定义 div → 移除）
  • 改 preload（metadata → auto → metadata）
  • 改容器比例（aspect-ratio → padding-top）
  • 去掉 fade-up 动画的 transform 干扰

结果：改了四轮，用户每次都说"还是拖不动"。

转折点：用户查到资料，说这可能是服务器不支持 HTTP Range 请求。我用 curl 逐平台实测，结果一目了然：

环境响应能否拖动
GitHub Pages206 Partial Content + 1024 字节✅
WorkBuddy 发布200 + 完整 3.7MB❌
本地预览服务200 + 完整 3.7MB❌
Cloudflare workers.dev打不开（国内不可达）—

真正的根因：不是代码，是托管平台是否实现 HTTP Range 分段请求。拖进度条时浏览器会发 Range: bytes=X-Y，服务器如果只会返回整个文件，浏览器就拿不到"那一小段"，于是回退到开头。

最终方案（前端可以彻底绕过）：

  1. 页面加载时先发一个试探请求（Range: bytes=0-1，拿到状态码立刻 abort，不浪费流量）
  2. 若是 206 → 正常流式播放
  3. 若是 200 → 说明服务器不支持分段，在用户第一次交互时把整个视频下载成 Blob，用 URL.createObjectURL(blob) 作为播放源
  4. 本地 Blob 不需要向服务器要分段数据，进度条从此任意拖动

教训：

先确定问题归属在哪一层，再改代码。

前端 → 服务器 → 域名/网络，三层要逐层排除。我一开始就在前端反复改，浪费了四轮迭代。一个 curl -H "Range: bytes=0-1023" 就能定位。

难题 2：Cloudflare 部署反复走错入口

现象：连续四次进入的都是 Worker 创建流程，而不是 Pages。

为什么会错：Cloudflare 新版把 Workers 和 Pages 合并到同一个入口，默认落在 Worker 上。Worker 的配置页有 npx wrangler deploy 这种字段——看到这个字段就说明走错了。

正确路径（查官方文档确认）：

Workers & Pages → Create application → 选 Pages 标签 → Connect to Git

或用直链 dash.cloudflare.com/?to=/:account/workers-and-pages。

识别口诀：

  • 看到「框架预设 / 构建命令 / 构建输出目录」→ Pages
  • 看到「npx wrangler deploy / 预览命令」→ Worker（走错了）

还踩过一个坑：连接 Git 时选成了 GitLab 账号，仓库列表为空（"No Git repositories found"）。代码在 GitHub 上，必须选 GitHub。

最终结论：即使部署成功，*.workers.dev 域名在国内无法访问（DNS/网络层），没有自有域名+备案就走不通。于是放弃 Cloudflare，回到 GitHub Pages + 前端瘦身。

难题 3：国内访问慢 —— 首屏要下 10MB

诊断：列出所有资源后发现，首屏实际要下载约 10MB：

  • 4 个隐藏弹窗里的 iframe（H5 1MB + 3 个 PDF 4.5MB）——只要 src 写了就会立刻下载，哪怕弹窗是隐藏的
  • 视频 preload="auto" 预载 3.7MB
  • 未压缩的 PNG（单张 476KB）

三步优化：

  1. iframe 的 src 改 data-src，点开弹窗才赋值，关闭时置 about:blank
  2. 视频 preload 改 metadata（只读头部，配合 Range 仍可拖）
  3. 图片压缩：476KB→12KB、98KB→15KB、38KB→3KB（Pillow，质量 82，最大宽 900px）

结果：首屏 10MB → 192KB，提升约 50 倍。

教训：

隐藏元素不等于不加载。iframe、img、video 只要写了 src 就会抢带宽。

优化前先算总量，不要凭感觉猜。

难题 4：CDN 加速反而不可用

原计划用 jsDelivr 给静态资源加速，实测 cdn.jsdelivr.net 在本网络下 SSL 握手失败（错误 35），主站 jsdelivr.com 却能打开——说明是 CDN 域名被限制。

连锁影响：云服务 SDK 和拖拽库默认都从 jsDelivr 加载，会直接导致功能失效。

解决：把两个依赖下载到本地，改成相对路径引用：

  • sdk-cloud.js（WorkBuddy 云 SDK，71KB，从 unpkg 拿到）
  • sortable.min.js（SortableJS，44KB）

教训：

不要假设"国外 CDN 一定能用"。上线前逐个资源测可达性，关键依赖本地化最稳——不依赖任何第三方域名。

难题 5：我误删了粒子动效（自己的操作事故）

现象：用户发现"顶部粒子动效不见了"。

原因：我用脚本替换首页的 loadDynamicProjects 函数时，用于定位结束位置的正则写错，把紧跟在后面的整段粒子系统代码一起删掉了。语法检查还能通过（因为删得"很整齐"），所以没被发现。

修复：从备份的旧版本里把粒子系统整段恢复，并重新部署。

由此建立的制度：

  1. 改主文件前，先复制一份到 历史版本/ 目录
  2. 大段替换后，必须 grep 校验关键函数是否还在（initParticles / playSound / fixVideoSeek / loadCloud）
  3. 所有历史版本导出成实体文件 + README.md 索引，可随时回滚

教训：

破坏性操作要有"事后自检"。语法通过 ≠ 功能完整。

正则/字符串替换是最容易"多吃一口"的操作，边界要格外小心。

难题 6：弹窗第二次打开是空白

现象：项目详情第一次能看，关掉再打开就空白。

原因：为了性能把 iframe 改成懒加载，关闭时把 src 设为 about:blank；再次打开时判断条件是 if(!f.getAttribute('src'))——而 about:blank 是非空字符串，判断为假，于是永远不再赋值。

修复：把 about:blank 也视为"未加载"。

教训：

用"占位值"表示"空状态"时，所有读取这个值的地方都要知道这个约定。否则就是埋雷。

难题 7：云服务不是"开了就能用"

接 WorkBuddy 云服务时遇到三个真实约束：

  1. Origin 白名单：云服务只接受它自己发布的域名（wbapp-xxx.app.workbuddy.host）发起的请求。GitHub Pages、本地预览都会被拒绝。→ 意味着"云端后台"只能在发布域名下用。
  2. 写入必须有身份：数据库有 RLS（行级安全），INSERT 时 owner_id 默认取 auth.uid()，未登录就没有身份，写不进去。→ 所以后台必须加登录。
  3. 表要自己建：云服务不会自动建表，要先 CREATE TABLE + 开 RLS + 写四条策略（公开读 / 本人增删改）。

教训：

"接后端"不是一个开关，而是一组约束条件的组合。先摸清边界（谁能访问、谁能写、数据放哪），再动手写代码。

难题 8：粒子光效迭代了六轮

用户的要求一直在细化，每一轮都是"更具体的感受"：

轮次需求实现
1参考 Logo 的橙红意象螺旋汇聚 + 中心瞳孔
2收放有节奏、有层次、带轻微体积光呼吸曲线 + 分层亮度 + 三层柔光
3弥散光粒子、星点消散柔雾层 + 全屏星点
4参考 v7、转速取中间值、光晕减弱、呼吸更快、边缘不规则改参数 + 角度扰动
5像篝火从下往上飞舞、光晕像音波起伏火星上升 + 音波环 + 不规则填充
6让它自己飘、经过时吸引粒子漂浮轨迹 + 引力场 + 环绕运动

关键技术点（第 6 轮）：

  • 光斑位置 = 两组不同频率正弦叠加 → 路径不重复，像"游走"而非"画圈"
  • 引力分三段：远处自由飘 → 中距离速度导向光斑 → 近处转切向环绕
  • 一开始粒子飞到核心就被"吞噬重生"，导致光斑周围反而变空（像黑洞）→ 改成环绕，并延长环绕时的寿命，才看得见

教训：

视觉需求很难一次说清，最好的沟通方式是"我先做出来给你看"。

我用 Python + PIL 把 canvas 的绘制逻辑重写了一遍，生成静态帧预览图，在部署前就能自查亮度/密度/分布——比"改完让用户看"快得多。

难题 9：移动端不是"缩小版桌面"

移动版真正要重做的是交互模型，不是 CSS：

桌面逻辑移动端必须改成
鼠标 drag 拖拽横向导航原生横向滚动 + 惯性 + scroll-snap 吸附
居中弹窗底部抽屉（85vh）+ 顶部把手 + 底部固定关闭键（单手可达）
:hover 反馈:active 缩放（手机上没有 hover）
canvas 粒子CSS transform 动画（移动端 GPU 更吃这个）
100vhcalc(var(--vh,1vh)*85) + 监听 resize（iOS 地址栏会让 100vh 出错）
点击区域随意所有可点元素 ≥44×44px（Apple HIG）

教训：

移动端适配的核心是手指的物理限制：够不到屏幕上方、容易误触、没有悬停。

设计的起点应该是"单手怎么用"，而不是"怎么把桌面版塞进来"。

二、贯穿全程的五条方法论

1. 先分层定位，再改代码

任何"不好用"的问题，先问：是内容问题、前端问题、服务端问题，还是网络/域名问题？

本次最大的一次浪费，就是在前端反复改了四轮，而根因在服务器的 Range 支持。

2. 用一条命令验证假设，而不是靠猜

curl -I、curl -H "Range: ..."、curl -o /dev/null -w "%{http_code}"——几秒钟就能把"猜测"变成"结论"。

3. 每一项优化都要有数字

不是"感觉快了"，而是"10MB → 192KB"。数字才能证明有效，也才能写进复盘和面试。

4. 破坏性操作必须备份 + 事后自检

备份到 历史版本/，改完 grep 关键函数。语法通过不等于功能完好。

5. 用"可验证的产出"代替"口头描述"

  • 粒子效果 → 先出静态预览图
  • 视频能否拖动 → 内置 ?selftest=1 钩子，把 seek 结果写进页面标题，用自动化读取验证
  • 部署是否成功 → 直接 curl 线上文件，确认代码特征字符串存在

类别内容

四、如果重来一次，我会怎么做

  1. 第一小时就测三个平台的 Range 支持，而不是先改前端

用 WorkBuddy 做网页 · 逻辑步骤指南

这份指南是我从零做完整套作品集（桌面端 + 移动端 + 云服务 + 双平台部署）后抽出来的方法。

不是"按钮在哪"的说明书，而是每一步该想什么、容易错在哪。

阶段一：定清楚「做什么」（30 分钟，决定后面 90% 的效率）

要定的事具体问题反面案例
目标受众面试官？客户？投资人？他们会用什么设备打开？只按自己的电脑做，手机上全乱
核心信息打开 5 秒内必须看到的一句话是什么？首屏全是装饰，看不到"你是谁"
内容清单有几个项目？每个项目有什么材料（图/PDF/视频/原型）？做到一半才发现没准备素材
主行动希望对方做的一个动作是什么？（下载简历 / 加微信）什么都能点，等于没有重点

产出：一张纸写清「受众 / 一句话定位 / 项目清单 / 主行动」。

这一步偷懒，后面每个细节都要回来补。

阶段二：让 AI 生成初版（对话式，不要一次性提完）

正确姿势：分块提需求，每块只描述内容与结构，不描述代码。

第 1 轮：这是个人作品集，受众是面试官，包含首屏 / 4 个项目 / 视频 / 联系方式。
        风格：深色、克制、专业。先出结构，不要动效。
第 2 轮：把项目卡片改成可点开看详情，详情里能嵌入 PDF 和 H5 原型。
第 3 轮：首屏加一层粒子光效，参考我 Logo 的橙红色系。

为什么分轮：一次给太多，AI 会平均用力，每块都做得勉强；分轮可以每轮验收。

关键提醒 AI 的三件事：

  1. 不引外部 CDN（很多域名在国内不可达）
  2. 大改前先备份文件到 历史版本/
  3. 改完要自检关键功能是否还在

阶段三：本地预览 → 小步迭代（最容易失控的阶段）

工作方式：一次只改一件事，改完立刻看效果。

顺序改什么为什么先改这个
1文案与结构内容对了，样式才有意义
2间距 / 字号 / 层级影响 80% 的"高级感"
3交互（点击、滚动、弹窗）决定好不好用
4动效最后加，否则会干扰前面的判断

这个阶段最容易出的事故：

  • ❌ 大段替换代码时误删相邻内容（我真删掉过整段粒子系统）

→ 规则：改前备份，改后 grep 关键函数名确认还在

  • ❌ 隐藏元素仍在加载资源（隐藏弹窗里的 PDF 全在下载）

→ 规则：iframe 用 data-src，点开才加载

  • ❌ 只看自己电脑（手机上排版全崩）

→ 规则：每轮改完都用手机打开一次

阶段四：性能优化（上线前必做，收益最大）

第一步：算总账

列出首屏要加载的所有资源及大小，加总。通常会发现一个"隐形大户"。

第二步：按收益排序优化

优化项做法典型收益
隐藏内容懒加载iframe 的 src → data-src，交互时才赋值一次省掉几 MB
视频不预载preload="metadata"省掉整个视频体积
图片压缩转 JPG/WebP，限制最大宽度，质量 80-85单张省 90%
依赖本地化CDN 资源下载到项目内避免域名不可达

验收标准：首屏总字节数下降一个数量级（我的是 10MB → 192KB）。

阶段五：版本管理（保证"改坏了能退回去"）

最小可行的做法（不用学 Git 也能用）：

  1. 项目里建 历史版本/ 目录
  2. 每次要大改前，复制当前文件进去，命名带日期和说明：

07_index_1116_导航轮播版.html

  1. 建一个 README.md 当索引，写清每个版本改了什么
  2. 版本文件只增不删

进阶（有 Git 更好）：

git add -A && git commit -m "描述这次改了什么"
git push

好处：每次提交都是可回滚的存档，而且能推送到 GitHub Pages 自动部署。

阶段六：部署（多平台，各有取舍）

平台对比（实测结论）

平台国内可达视频拖进度条静态站免费备注
GitHub Pages可（偏慢）✅ 支持 Range✅最稳，推荐主用
WorkBuddy 发布可❌ 不支持 Range✅支持云服务，适合做后台
Cloudflare Pages视情况—✅workers.dev 国内常不可达
本地预览仅本机❌—仅开发用

关键判断：视频能不能拖进度条？

curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Range: bytes=0-1023" https://你的域名/视频.mp4
  • 返回 206 → 服务器支持分段，原生可拖
  • 返回 200 → 不支持，需要前端 Blob 兜底

GitHub Pages 部署（最省事）

  1. 建仓库：用户名.github.io
  2. 本地 git push
  3. 仓库 Settings → Pages → 选 main 分支 → 根目录
  4. 访问 https://用户名.github.io

WorkBuddy 发布

  • 用发布功能直接产出在线链接，适合需要云服务（数据库/登录）的项目
  • 注意：云服务的接口有 Origin 白名单，只在发布域名下可用

阶段七：云服务接入（需要"真后端"时）

先判断是否真的需要：

  • 只有你自己改内容 → 用本地管理工具 + 手动更新HTML 就够
  • 希望别人也能看到你后台新增的内容 → 才需要云数据库

标准流程：

1. 激活环境（inspect → activate，复用已有应用）
2. 建表（CREATE TABLE，字段：id / owner_id / 业务字段 / created_at）
3. 开 RLS + 写策略（公开读 + 仅本人增删改）
4. 前端接入（初始化 SDK → 读 / 写 / 删）
5. 后台加登录（写入需要身份，OAuth 或验证码）
6. 验证（写一条 → 首页能读出来 → 删除）

三个必知的坑：

  1. 写入必须有登录身份，否则被 RLS 拒绝
  2. Origin 白名单：换个域名调用会被拒（所以云功能只在发布域名生效）
  3. SDK 不要依赖 CDN，下载到本地更稳

阶段八：移动端适配（不是缩小版桌面）

要重做的四件事：

桌面移动
多列布局单列垂直流
鼠标拖拽原生横向滚动 + scroll-snap 吸附
居中弹窗底部抽屉（85vh）+ 底部固定关闭键
:hover:active 缩放反馈

必查清单：

  • ☐viewport 含 viewport-fit=cover，禁用手势缩放
  • ☐overflow-x: hidden（html 和 body 都要）
  • ☐安全区：env(safe-area-inset-bottom) 给底部留空间
  • ☐可点元素 ≥ 44×44px
  • ☐正文字号 ≥ 14px，标题 20-24px
  • ☐抽屉用 transform 动画，不用 height
  • ☐复杂 canvas 换成 CSS 动画（省电、不卡）
  • ☐视频加 playsinline，否则 iOS 强制全屏

阶段九：验证与交付

不要"觉得没问题"，要"证明没问题"：

要验证的验证方法
页面能打开curl -o /dev/null -w "%{http_code}"
新代码已生效`curl ... \grep 特征字符串`（如函数名）
视频能拖内置 ?selftest=1 钩子，把结果写进页面标题
移动端布局真机打开，或用浏览器设备模拟
所有弹窗能开逐个点开、关闭、再点开（验证第二次不空白）

交付物清单：

  1. 桌面端链接
  2. 移动端链接 + 短链
  3. 二维码（扫码直达，绕开微信内置浏览器）
  4. 源码 + 版本归档
  5. 后台地址与使用说明

附：一整轮的节奏建议

时间做什么
30 分钟定受众、定位、内容清单
1-2 小时生成初版 + 结构确认
2-4 小时内容填充 + 样式打磨
1 小时交互与动效
30 分钟性能优化
30 分钟部署 + 验证
1-2 小时移动端适配
按需云服务接入

真正耗时的从来不是写代码，而是"改了半天发现方向错了"。

所以：先定方向 → 小步验证 → 及时备份 → 用数据确认。
